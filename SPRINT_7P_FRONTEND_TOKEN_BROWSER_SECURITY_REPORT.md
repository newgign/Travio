## Storage changes and semantics

New services/authStorage centralizes auth persistence in sessionStorage, retaining keys token/user. On access it removes only legacy localStorage token/user; never copies legacy token, never touches preferences. All identified direct auth reads/writes now use the abstraction. Admin logout uses the existing session.logout event/cleanup flow. Login partial storage-write failure removes session keys and emits fixed AUTH_STORAGE_UNAVAILABLE; no persistent fallback. Existing profile validation, stale-response protections,401/404 behavior,403/5xx/network policy and bearer extraction contract retained. User-facing help storage name updated. No backend runtime changes or cookie auth migration.

One fresh login is required for users whose only session was legacy localStorage. Same-tab reload remains supported and server-validated. Tabs no longer share ongoing login/logout through localStorage; no BroadcastChannel sync added. A fresh independently opened tab may be guest; browsers may clone sessionStorage from an opener/duplicated tab, after which stores diverge. Normal tab close ends tab persistence, but browser session restore/reopen behavior can preserve sessionStorage. Therefore browser-close erasure and zero cross-tab inheritance are NOT guaranteed. Active bearer remains readable by same-origin JavaScript; sessionStorage reduces persistence, does not prevent XSS theft. Storage denial can prevent physical removal of legacy browser data; the app never reads/promotes that token. Future operational account/session revocation remains server controlled.

No token added to URL/query/hash/returnTo/history/DOM/debug helpers. Synthetic sentinel tests exercise request URL, auth error, auth rendering and storage behavior. Existing generic non-auth API error/data handling is not a universal arbitrary-secret redactor.
